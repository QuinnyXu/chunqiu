2. **新增条款**：§7「私有层与叙事分层」内，紧接 v1.29 通例「判定反转须如实记录，不得抹平」之后、原「交付文档命名规范」一节之前，新立小节 **「交付体例·实测口径（v1.31 新增，r38 立）」**，收录通例：

   > **提交哈希与 Actions 运行号一律待动作完成后实测回填，不得预填**：交付文档「提交」「生产」一类表格栏目中的 git 提交哈希与 GitHub Actions 运行号，只允许在对应的 `git commit`／`git push`／Actions 运行实际发生之后、以实测手段（`git log`、`gh run list`、`gh run view` 等核验所得）回填；不得在动作尚未发生前按预期先填一个"届时应当是"的占位值，即便打算随后再订正也不许预填在先。

   条文中引注病例 `docs/delivery_vision_r37.md` §十.0，写明失误形态（预填了尚不存在的 `0a9f1ef`／Actions `31976886766`，实为 `6fa1851`／`31976930936`）与立条理由（交付文档体例通篇以「实测不是推断」自律，预填正是这条自律最隐蔽的一处失守，且这一栏读者最难辨真假——数字外观与其余实测字段无异，默认即是抄自 `git`／`gh` 实际输出）。

3. **落点编排理由**：原「交付文档命名规范」一节（v1.6 所立，管"文件叫什么"）与上方几条二手引述/判定反转类通例（管"史料注文的核对纪律"）均未覆盖交付文档**自身**核验类数字的实测/推断之辨——查遍全文（`grep -n "运行号\|提交哈希\|Actions" docs/conventions.md`）此前零命中，确系空白，故就近立目而非塞入既有条款。
4. **互指处置**：新条款与 §7 v1.29 通例「判定反转须如实记录，不得抹平」双向互指——
   - 新条款正文写明：「与 §7 v1.29 通例『判定反转须如实记录，不得抹平』…同一道防线，彼条管史料判定的反转记录，本条管工程记账的预填失守，尺度不因领域而两样」；
   - 反向在 v1.29 通例原句末追加一句回指：「（互指：v1.31 新增『提交哈希与运行号一律实测回填，不得预填』通例——史料判定的反转记录与工程记账的预填失守是同一道防线…）」。
   - 未发现其他相邻条款以「复验结论须实测」「不得以应当如此代替」为正式标题成文（`grep` 全文零命中此类固定措辞），故互指对象只此一处，未强行拼凑额外互指。
