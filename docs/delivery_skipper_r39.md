# 交付说明 · Skipper r39（微任务）—— conventions 升 v1.32：v1.31「实测回填」条补自引边界

## 一 · 任务来源

【微任务 For Skipper】：conventions 升下一号，为 v1.31「交付体例·实测口径」通例（提交哈希与 Actions 运行号一律实测回填、不得预填）补一个**自引边界**——该条要求的"实测回填"动作本身也是一次提交、也触发一次 Actions，若逐次都要求"回填了就再入表回填一次"，则无穷回归。边界由 Vision 在 `docs/delivery_vision_r38.md` §六／§七 首例实做并主动提请，站长裁定采纳，派交本轮落地写入正文。

## 二 · 本件改动面

只动两处，均在 `docs/conventions.md`：

1. 顶部版本行：新增 `版本：v1.32`，原 `v1.31` 行降为 `历史：v1.31`（既有正文原样保留，未回改）。
2. §7「交付体例·实测口径」节内、v1.31 原条款末尾——**紧接原条款、不另立小节**，追加一段边界判例：

   > **边界（v1.32 新增，r39 补，源出 `docs/delivery_vision_r38.md` §六／§七 Vision 首例实做及自曝疑点）·回填链截断于追记提交**：上条要求"实测回填、不得预填"，但未言明回填动作**自身**——它也是一次提交、也触发一次 Actions——是否也须再入表回填；若逐次都要求"回填了就再回填一次"，则永无终点。裁定：**回填链截断于追记提交；收尾提交之运行号口头上报、不入表。**即交付表格只需完整记录到"补齐哈希与运行号的那一次追记提交"为止——该追记提交自身的哈希与运行号仍须照旧实测回填入表；此后若还有一个仅用于确认"追记提交已成功部署"的收尾提交，其自身的哈希与运行号不再要求入表，改为口头向领队上报即可。**理由**：**档案完备以可核为界，其后链条由仓库自证**——交付文档入表的意义在于让读者拿着这一格数字去仓库核对；而回填之后的每一次提交，本身已经完整记在 git 提交历史与 Actions 运行记录里，任何人随时可 `git log`／`gh run list` 自行追溯到底，文档没有必要、也不可能对这条链条做穷举式的登记——登记的义务止于"把读者引导到可核实的起点"，起点之后的链条本身即是自己的证据。**首例**：`docs/delivery_vision_r38.md` §六——该件回填到追记提交 `d238728`（Actions `31978021663`）为止入表，其后的收尾提交（实为 `be87d6e`）之运行号未入表，按本条应作口头上报处理；本条即据该件 §七 主动提请、由站长裁定正式确认为通例。

`data/csv/`、`site/`、`tools/` 均未触及，与任务书要求一致。

## 三 · 与 v1.31 原条款的衔接措辞

v1.31 原条款末句为："本条自本版起对全体角色的交付文档一体生效……即本条一经写入，第一个必须照此实测回填的交付文档就是记录本次改动的那一份。" 新增边界句紧接其后，同一段落内以"**边界（v1.32 新增……）**"另起一个粗体判例标签衔接，读者读完 v1.31 原条款（"不得预填，必须实测回填"）后立即读到本条边界（"填到追记提交为止即可，收尾提交口头报"），语义上是"知道要填、也知道填到哪为止"的完整闭环，不会误读为"每次回填都要再回填"。
